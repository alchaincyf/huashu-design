# 打磨环：看图、挑刺、改，再看

第一版写完只是一份草稿。设计师和写代码的人差别最大的地方就在这里：写完之后坐回去看，看出哪里不对，改，再看。
同一个模型，看过自己的截图再改三轮，和写完就交，产出差一个档次。这份文件讲怎么看、看什么、看几轮。

## 怎么看

```bash
# $HD = 本 skill 的根目录
python3 "$HD/scripts/polish.py" shot <页面.html> --mobile      # 逐屏截原尺寸图，存到 polish/<文件名>/round-N/
```

它把页面按视口高度切成一屏一屏的原尺寸截图，并在项目里的 `polish-log.md` 追加这一轮的记录。
然后用看图能力**逐张打开**这些截图。整页长截图缩成一张看，字和间距都糊了，问题看不出来——一定要一屏一屏看原图。

deck 不滚动，一页就是一屏：用 `gen_deck_thumbs.mjs` 或 `verify.py --slides N` 出每页的图，同样逐张看。
动画看关键帧，走 `references/modules/motion.md` 里的校验。

脚本打印的数字（每屏几个图形、多少字、底色占多少）只是提示你先看哪里，不能代替看图。
没装 playwright 时用手头任何截图办法逐屏截，照下面的问题看。没有看图能力的 runtime 见文末。

## 看什么

每一轮带着这八个问题看，把答案里**最伤的三处**写进 `polish-log.md`，写到「哪一屏、哪个元素、怎么不对」：

1. **首屏三秒**：没看过这个项目的人，三秒内看得出这是什么、给谁的吗？这个题材世界里独有的东西出现在第一眼里了吗？
2. **主角素材**：方向卡里写的主角素材到位了吗？内容必需的图在不在——介绍 App 的页面看得见 App 的界面吗，讲数据的页面数据成了画面吗？
3. **每一屏的事件**：往下滚，每一屏有没有一个让人停一下的东西，还是「小标题＋三张卡片」重复到底？
4. **层级**：眯起眼看每一屏，最先跳出来的是不是最重要的那个？
5. **手艺**：对齐、间距的节奏、行尾的孤字、难看的断行、溢出、裂图、和周围不是一套的元素。
6. **手机**：窄屏下同样的问题再问一遍——不是「没坏」就行，是在手机上也像被设计过。
7. **对照方向卡**：把截图和方向卡、参考板（或样张）并排看，「借的是什么」里写的那几条规则落实了吗？走样在哪？
8. **摘一件**：去掉哪一样东西，这一屏反而更好？

脚本提示「连续几屏只有文字和框」「接近空屏」时，第 3 问多半已经有答案了。
安静留白的方向会被提示底色占比高，那是它的本意，不用为了让数字好看去填东西。

## 改什么

一轮只改最伤的三处，改完重新截图再看。不要一轮里顺手改十几处——改多了看不出哪个改动起了作用，也容易把好的地方改坏。
先改结构性的（首屏不成立、主角素材缺席、整屏平庸），再改手艺上的。

哪一屏怎么看都平庸，别修修补补，把这一屏推倒重做：换一种组织信息的办法。
重做前先问：一家顶尖工作室接了这个项目，会在这一屏上多花三天做什么？

## 看几轮

| 阶段 | 轮数 |
|---|---|
| 三方向的每个初稿 | 1 轮：截图、看、改最伤的三处。初稿是给用户选方向的，不用磨到完工 |
| 选定方向后的正式版 | 至少 2 轮；到某一轮认真看完找不出值得改的三处为止，通常 3–5 轮 |
| 用户赶时间 | 1 轮，交付时说明只打磨了一轮 |

到第 5 轮还在大改，说明问题在方向或结构上，不在打磨上：停下来，把看到的问题和两个可选的改法告诉用户。

每一轮的截图都留着。交付时把第一轮和最后一轮首屏并排给用户看一眼，他能看到这几轮改了什么。

## 没有看图能力时

读不了截图的 runtime 没法真正打磨，但别跳过：跑 `polish.py shot` 拿到每屏的事实，跑 `design_lint.py check` 修红灯和黄灯，
然后照 `references/steady-track.md` 的页面清单逐条对。交付时如实说明「这一版没有经过看图打磨」，并把截图路径给用户。
