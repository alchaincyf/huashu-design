# 模块 · 微信小程序

微信小程序的界面原型、改版、换皮走这里。小程序不是缩小的 App，也不是塞进手机的网页：它住在微信里，右上角永远有微信的胶囊，用户多半是从一张群聊卡片或一张桌贴二维码进来的，用完就走。先过 SKILL.md 的窄桥，再按这份手册做；App 原型手册（`references/app-prototype.md`）里的形态先行、八条范式、展示板、真图，这里照样适用。

定稿之后可以直接交给 WorkBuddy 做成真的小程序，见文末「交给 WorkBuddy」。

## 窄桥一 · 规格（微信的要求，照字面做；2026-11 核对）

| 项 | 规定 | 来源 |
|---|---|---|
| 设计稿宽度 | 按 375 宽画（也可 390）。375 宽时 750rpx 等于屏幕宽，**1px = 2rpx** | 小程序设计指南「设计稿标准尺寸」、WXSS 文档 |
| 右上角胶囊 | 所有页面都有，开发者不能改内容，只能选深浅两种配色；设计时留出位置，旁边别放可点的东西 | 设计指南「小程序菜单」 |
| 胶囊位置 | iPhone 刘海屏常见值：87×32，距顶 48，距右 7，状态栏 44，导航栏内容区高 40；安卓和不同版本会差几 px，代码里用 `wx.getMenuButtonBoundingClientRect` 取，别写死 | 社区实测（设计稿按这组画即可） |
| 导航栏 | 默认导航栏：标题居中，背景色任选，文字只能黑或白；`navigationStyle: custom` 自定义：整个顶部自己画，只剩胶囊 | 全局配置 window |
| tabBar | 最少 2 个、最多 5 个（建议不超过 4 个）；一个页面只能有一组；可在底部或顶部，顶部时不显示图标；原生图标 PNG、建议 81×81、每个不超过 40KB、不能用网络图；也可以 `custom: true` 自己画 | 全局配置 tabBar、设计指南 |
| 代码包 | 主包和单个分包各不超过 2MB；全部分包不超过 30MB，服务商代开发的不超过 20MB（WorkBuddy 以第三方服务商身份托管发布，按 20MB 算更稳） | 分包加载文档 |
| 转发卡片 | 群聊里那张卡的图显示比例 **5:4**；收藏用 1:1 | Page.onShareAppMessage / onAddToFavorites |
| 字号 | 微信常用 22、17、15、14、12pt；正文别小于 12px | 设计指南「字体」 |
| 点按热区 | 物理尺寸约 7–9mm，约 44px 见方 | 设计指南「避免误操作」 |

运营规范里管界面的那一条（13 小程序 UI 规范）照字面守：符合设计规范；**不得改变微信的外观和功能**（别把页面做成微信聊天、朋友圈、支付页的样子）；图片上的文字要简洁，**不要用文字挡住图片**（大字压满全图的海报式首屏要克制，主体露出来）；浮层和弹窗都要能关；不得模仿系统通知诱导点击；页面下拉时，顶部的小程序账号名要看得清，别用背景色盖住它。混淆行为（5.14）也相关：登录页、弹窗里别用微信的 logo 和「微信官方」口吻；主色别默认用微信绿。

规格每年会调，上线前以微信开放文档为准。

## 窄桥二 · 画得出来，就要做得出来

小程序是原生 WXML／WXSS，不是浏览器。设计稿里出现的东西，开发要能照着写出来，否则交出去的就是一张做不出来的图：

- **本地图片用 `<image>`**，不要写成 CSS 的 `background-image`（原生工程里本地图不能这么引用）。设计稿里也照这个写：图放进 `<img>`。
- **图要算体积**。主包只有 2MB，设计里的照片压成 JPG，最长边 1000px 左右；一屏一张大图可以，一屏十张大图要放云存储。`mp_handoff.py` 会把合计体积报出来。
- **字体**：默认用系统字（苹方）。要用一款展示字体，就只用它写标题，并接受它要 `wx.loadFontFace` 加载、裁成子集（只留用到的字）；一个小程序一两款为止。
- **毛玻璃（backdrop-filter）**部分安卓机不稳，可以用，但去掉它设计也要成立。
- **Three.js、大段 canvas 动画、视频背景**在小程序里代价很高；签名交互优先用 CSS 过渡、一个 `<canvas>` 画的小图形、或者 `<movable-view>` 拖动。
- 地图、视频、相机、直播是原生组件，设计里可以有，但别在它们上面压复杂的浮层。
- 状态要画全：loading、空状态、出错、未登录。小程序没有「安装」这一步，第一次打开时什么都没有，空状态往往就是首屏。

## 先想它从哪被打开

App 的首页是用户自己点开图标看到的；小程序的「首屏」常常不是首页。做方向卡之前先回答：**这个小程序最常从哪进来？**

| 入口 | 用户当时的状态 | 设计上意味着 |
|---|---|---|
| 群聊里的一张卡片 | 朋友发来一件具体的事：拼单、报名、投票、一篇内容 | 卡片点进来落在那件事本身，不是首页；转发卡片本身就要设计 |
| 扫一张码（桌贴、海报、门口立牌） | 人在现场，一只手拿手机，可能在排队 | 首屏就是要做的那件事：点单、取号、签到；字大、步骤少 |
| 搜一搜、下拉「最近使用」 | 回头客，知道自己要什么 | 首页给熟客的捷径：再来一单、上次的座位、我的预约 |
| 公众号文章、视频号里的链接 | 被内容带过来，还没决定 | 先给看的，再给做的；不要一进来就要授权 |
| 朋友圈 | 打开的是单页模式，不能跳转 | 被分享到朋友圈的那一页要自己讲得通 |

所以每个方向卡在 App 手册那五件事（主屏形态、签名处、数据的形状、颜色回答什么、嗓音）之外，再写两件：**主入口是哪一个、转发卡片长什么样**。

## 和 App 不一样的地方

- **即用即走**。一次使用常常不到一分钟。首屏只放一个主动作，第二个动作往下放。
- **先用后登录**。浏览不要求登录，到了要存数据、下单、报名那一步再弹登录；用户拒绝也能接着看。微信的运营规范要求拒绝授权后要清掉用户的头像昵称、要有容易找到的退出。
- **微信已经在屏幕上了**。胶囊、默认导航栏的位置是固定的，你的品牌只能在剩下的地方出现。自定义导航栏让顶部整个归你，但胶囊还在——把它当成构图里一块不能动的石头。
- **tabBar 不是必需品**。服务型小程序（点单、预约、报名）很多只有一条主流程加一个「我的」，两三个 tab 甚至不要 tab；内容型才需要四五个。
- **转发卡片是第二张首屏**。用户在群里看到的只有：小程序名、一两行标题、一张 5:4 的图。这张图要在聊天气泡那么大的时候读得出（标题六到十二个字，一个主体），并且和点进去的那一页一致。每个方向都画一张，放在展示板上的聊天气泡里（`WechatShareCard`）。
- **订阅消息代替推送**。要提醒用户（取餐、开课、到号）时，设计里画出「订阅一次」的那个时机和文案，别假设能随时推。

## 从外壳起步

```jsx
// Read 本 skill 的 assets/wechat_frame.jsx，把整个文件贴进你的 <script type="text/babel">
<WechatFrame page="pages/menu/menu" title="点单" tab="点单"
  tabBar={{ list: [{ text: '点单' }, { text: '订单' }, { text: '我的' }], selectedColor: '#2B4A3A' }}>
  <MenuScreen />          {/* 内容从导航栏下面开始；自定义导航栏时从屏幕最顶上开始，自己避开胶囊 */}
</WechatFrame>

<WechatShareCard appName="小满咖啡" title="今天的燕麦拿铁第二杯半价">
  <img src="…" style={{ width: '100%', height: '100%', objectFit: 'cover' }} />  {/* 5:4 */}
</WechatShareCard>
```

- 不要自己画状态栏、胶囊、home indicator，外壳都有；也不要用 `assets/ios_frame.jsx` 套小程序（宽度和顶部高度都不对）。
- `page` 写成小程序的页面路径（`pages/<名字>/<名字>`），交付包按它生成 app.json 的页面清单；小程序打开的第一页加 `home`（不标就按 tabBar 顺序排）。
- 展示板上可以把手机缩小、错落摆放，交付包会按 375 原尺寸截；同一页画了两种状态（比如有数据和空状态），就放两台、`page` 写同一个。
- 打磨截图不加 `--mobile`：展示板是给人在电脑上看的，手机本身已经在板上。
- 自定义导航栏：`nav="custom"`，顶部 84px 自己画，标题放在胶囊左边，和胶囊垂直居中对齐（胶囊中线在 y=64）。
- 只有 tab 页才传 `tabBar` 和 `tab`；详情、确认、凭证、门店这类二级页不传，真小程序里它们左上角是返回、底下没有 tabBar，空出来的那块要一起设计。
- 固定在底部的结算条、报名按钮、购物车，放进 `footer`（在 tabBar 上方，不跟内容滚）；不要在 children 里写 `position: fixed`。
- 一屏有几种状态（分类筛选、空状态、售罄）时，每种要交给开发的状态各放一台手机，交付包只截每台手机当前的样子。
- 自己画 tabBar：不传 `tabBar`，把你的组件放在 children 底部，加 `data-mp-tabbar="custom"`，留出底部 34px 安全区。
- 展示板照 App 手册「展示板」：主次、流程串联、局部特写、语境底，三个方向构图不同；转发卡片放进一小块聊天背景里，摆在展示板一角。起步用 `assets/showboard.jsx`（`aside` 放转发卡片），三个方向各选一种 `layout`。

## 三方向门在这里的样子

每个方向一个完整 HTML：展示板上 4–5 屏（每屏都能点）＋一张转发卡片。六个候选照 `references/directions.md` 构思，现实参照可以是 App Store 的 App（`appstore_shots.py`），也可以是你亲眼见过的好小程序——小程序没有商店截图可取，参照写清名字和你借的是哪一层。

三个方向至少在这几项里有三项不同：主入口按哪个设计、首屏形态、签名处、颜色回答什么、有没有 tab。微信绿、白底灰卡片、顶部一张轮播图、金刚区一排圆形图标，是小程序最常见的默认答案，只有它真的最合适时才用。

## 定稿后：导出交付包

选定方向、正式版至少打磨两轮之后：

```bash
python3 "$HD/scripts/mp_handoff.py" "<定稿>.html" --name "<小程序名>"     # 默认写到同级的 _design/
```

出 `screens/`（每屏 750 宽，1 像素＝1rpx，可滚的屏另出长图）、`share-N.png`、`images/`、`tokens.json`、`README.md`（页面清单、app.json 骨架、颜色字号圆角、图片体积、体检）、`给WorkBuddy的话.md`。✗ 必修（字或按钮压在胶囊上、tab 数量不对、转发卡片不是 5:4）；! 逐条看，有意为之可以留。

逐张打开 `screens/` 看一遍：截图就是开发要照着做的东西，截出来不对，做出来也不会对。

## 交给 WorkBuddy

WorkBuddy 能把原生小程序写出来、预览，并以微信第三方服务商的身份帮用户发试用版、体验版和提审，不需要开发者工具。交付包就是给它读的。

**你就在 WorkBuddy 里**（`capabilities.py` 报「WorkBuddy / CodeBuddy」）：方向选定、交付包导出后，问用户一句要不要直接做成真的小程序。要的话就在当前会话里接着做：按 WorkBuddy 内置的小程序开发流程在一个新的空目录建工程，建好后把 `_design/` 整个拷进工程根目录，再照 `_design/给WorkBuddy的话.md` 开工；数据存本地还是云端，用户没说就问这一项。后面的开发、预览和发布按 WorkBuddy 自己的流程走，这份手册不管。

**你在别的 agent 里**（Claude Code、Codex……）：交付包导出后告诉用户三步——打开 WorkBuddy，新建任务时选「代码开发」里的「小程序」；把交付包所在的文件夹发给它（作为工作空间，或把文件夹拖进对话）；把 `给WorkBuddy的话.md` 的内容贴进去，补上数据那一句。

不管在哪：不要替用户发布（试用版、体验版、正式版都要他扫码授权），也别说「已上线」；交付时写清做到了哪一步（设计稿／交付包／工程已生成／预览已核对）。
